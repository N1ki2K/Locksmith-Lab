# Security changes: Unsecured and Secured

The Secured application preserves the Unsecured workflow while fixing the weaknesses below. Run the examples against local instances only. The integration suite in `api/test/security.test.ts` exercises the secured behavior against a dedicated test database.

| Issue | Unsecured source | Secured implementation | Why it changed | Reproducible comparison |
| --- | --- | --- | --- | --- |
| SQL injection in login and registration | `unsecured/api/src/repositories/userRepository.ts` interpolates credentials into SQL. | `secured/api/src/repositories/userRepository.ts` binds username and hash as query parameters. | SQL syntax from input must remain data, not alter a query. | On Unsecured, submit username `' OR '1'='1' --` to login with any password and observe the bypass. On Secured, the username is rejected by validation; SQL-like text in a note title/content persists literally. See tests for this case. |
| SQL injection in notes | `unsecured/api/src/repositories/noteRepository.ts` interpolates IDs and note fields. | `secured/api/src/repositories/noteRepository.ts` passes every value in a parameters array. | Note contents and IDs must not become executable SQL. | Submit a note containing `'); DROP TABLE notes; --` on each app and verify it is displayed as text; Secured stores it without changing the schema. |
| Plaintext password storage | `unsecured/api/src/repositories/userRepository.ts` stores and compares the submitted password directly. | `secured/api/src/services/authService.ts` hashes and verifies with Argon2id; repository responses omit hashes. | A database disclosure must not reveal users' passwords. | Register a user and inspect `users.password` in PostgreSQL: Unsecured stores the literal password; Secured stores an encoded `$argon2id$...` hash. The secured API user object has no password property. |
| Note IDOR / broken ownership checks | `unsecured/api/src/repositories/noteRepository.ts`, `unsecured/api/src/services/noteService.ts`, and `unsecured/api/src/controllers/noteController.ts` operate by note ID without consistently passing the owner. | `secured/api/src/controllers/noteController.ts`, `secured/api/src/services/noteService.ts`, and `secured/api/src/repositories/noteRepository.ts` carry `req.session.userId` through all operations; read/update/delete SQL uses `id = $1 AND user_id = $2`. | Authentication alone does not establish ownership of a referenced object. | Create one note as account B. As account A, request, update, and delete B's ID. Unsecured permits the affected operations; Secured returns the same 404 for all three. Tests assert this. |
| Session fixation and cookie exposure | `unsecured/api/src/index.ts` uses hardcoded `password123`, `httpOnly:false`, and the in-memory store; `unsecured/api/src/controllers/authController.ts` sets identity without rotating the ID. | `secured/api/src/index.ts` requires `SESSION_SECRET`, sets `httpOnly`/`sameSite`, production `secure`, eight-hour expiry and PostgreSQL storage. `secured/api/src/controllers/authController.ts` regenerates the ID on login and destroys on logout. | Session credentials and identifiers need protected storage and lifecycle. | Compare the session cookie before and after a successful login; Secured issues a new ID. Inspect Secured cookie flags and verify logout makes `/api/notes` return 401. |
| CSRF and browser headers | `unsecured/api/src/index.ts` has credentialed CORS but no CSRF mechanism or Helmet. | `secured/api/src/middleware/csrfMiddleware.ts` requires a session-bound header token for writes; `secured/api/src/index.ts` configures explicit CORS and Helmet. | A browser should not be able to trigger authenticated writes from another origin. | Send `POST /api/auth/register` or `/api/notes` without `X-CSRF-Token`: Secured returns 403. Fetch `/api/csrf-token`, then repeat with the token and valid session. |
| Weak input validation and error leakage | `unsecured/api/src/controllers/authController.ts` and `noteController.ts` check only presence or coerce IDs. | Secured controllers enforce formats, types, lengths, positive integer IDs and exact note fields; `secured/api/src/index.ts` logs server failures and returns a safe generic response. | Invalid or unexpected data should be rejected before database access and internal details should not reach clients. | Try `/api/notes/0`, `/api/notes/1abc`, oversized title/content, non-string fields, or an extra `user_id` field. Secured returns HTTP 400. |
| Login guessing and duplicate account race | Unsecured auth controller has no login limiter and checks name availability before insertion. | `secured/api/src/index.ts` limits login attempts; `secured/api/src/services/authService.ts` handles PostgreSQL unique violations after the insert. | Slow repeated password guessing and concurrent duplicate registration attempts. | Make more than 10 failed login requests in 15 minutes for the same IP; Secured returns 429. Register a duplicate username; Secured returns 409 without exposing database details. |
| Invalid schema defaults and shared database | `unsecured/database/init.sql` uses invalid PostgreSQL `DATETIME` defaults; `unsecured/docker-compose.yml` has its own database. | `secured/database/init.sql` uses `TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP`, checks and a user-note foreign key. `secured/docker-compose.yml` uses host port 5433, a distinct container and volume. | Fresh PostgreSQL 17 initialization must work and the comparison databases must not overlap. | Start with `cd secured && docker compose up -d database`; inspect schema and `\d notes`. Confirm Unsecured's compose project and Secured's named volume/ports are distinct. |

## Validation and limits

The integration suite uses a dedicated database whose name includes `test`; see the setup in `README.md`. It intentionally verifies that a foreign note ID is indistinguishable from a missing one. The login limiter uses the Express process's client IP; behind a reverse proxy, set `TRUST_PROXY=true` only when exactly one trusted proxy sits in front of the API. The supplied local configuration uses HTTP and therefore leaves the `Secure` cookie flag off; production must use HTTPS and `NODE_ENV=production`.
